# Seam

> **当前状态：v0 已完成**，即带完整事件日志的命令行 agent。下文描述的解释功能是 v1 及以后的设计目标。

## 为什么需要 Seam？

现有的 agent 产品大多追求“无缝”的体验：agent 循环、上下文组装、工具执行全部藏在界面背后。用起来很顺手，但用户因此形成了错误的心智模型：

- 以为 agent **记得一切**，其实模型本身没有记忆，是 harness 每轮重发历史，过长时还会裁剪；
- 以为它**看过整个文件夹**，其实它只看到被读进上下文的那几个文件；
- 以为它**亲手在电脑上操作**，其实模型只是提出请求，由 harness 执行并把关。

错误的心智模型会直接导致两类失败：**过度信任**一个只读了三个文件就得出的结论；以及出错时**无从判断原因**。

可观测性工具（Langfuse、LangSmith 等）能把这些细节展示出来，但它们是给开发者用的。面向普通用户、以建立正确心智模型为目标的解释设计，几乎还是空白。

## 核心理念

**Seam** 取自 HCI 中的 *seamful design*：与其把系统的“缝”全部抹平，不如在关键处有意露出来，帮助用户建立正确的理解和恰当的信任。

Seam 的核心 agent 能力只做最小子集，把差异化的投入全部放在以人为中心的透明性和可解释性上。**功能面积小、解释深度大**，这个比例本身就是设计主张。

### 设计原则

1. **每个功能纠正一个误解，或打开一个插手点。** 答不上来“它纠正了什么、打开了什么”的功能，就不做。
2. **事实与自述分离。** harness 记录的客观事实（调用了什么、返回了什么），与模型自己给出的理由使用不同的视觉样式；后者统一标注“模型自述”。
3. **分层披露。** 每个动作都可以从一句话的故事逐层展开到原始请求，默认只显示最简单的一层。
4. **来源可追溯。** 上下文里的每段内容、每个结论，都能追到它的来源：用户、本地文件、网页、记忆或 Skill。
5. **拥有循环。** 工具、系统提示词和上下文组装全部自己实现，每一轮发给模型的完整请求都会被记录，可以被精确呈现。
6. **解释必须可行动。** 用户看懂之后，应当能在同一处做出纠正或决定。

## 要纠正的误解

| 常见误解 | 真实机制 | Seam 的做法 |
| --- | --- | --- |
| agent 是黑箱，丢进去等结果 | 它按计划多轮推进，每轮都可能调整 | 任务地图：实时标出当前步、已完成步和偏离计划的步 |
| 它看过我整个文件夹 | 它只看到被读进上下文的内容 | 阅读覆盖图：读过的文件点亮，没读过的保持灰色 |
| 它讲的理由就是它这么做的原因 | 模型自述不一定反映真实的决策过程 | 事实与自述用不同样式区分 |
| 它的结论一定有依据 | 结论可能来自不完整的读取 | 结论溯源：每个论断都能跳到对应的原文位置 |
| 它亲手在我电脑上操作 | 模型只提出请求，harness 执行并把关 | 权限确认框说明“这是模型的请求，由 harness 拦下交给你” |
| 它记得我说过的一切 | harness 每轮重发历史，过长时裁剪 | Agent 的书桌：看得见、改得了的上下文（v2） |
| 网页上的话不会影响它 | 网页内容与用户指令一样进入上下文 | 来源标记与注入提醒（v3） |

## 它如何工作

Seam 的每个事件都写入同一份事件日志，解释层只读这份日志来生成所有解释，所以界面上展示的事实与实际执行永远一致。

```
界面层（本地 Web）   ← 渲染解释；用户的审批与干预回到权限闸门和下一轮上下文
     ▲
解释层               ← 从事件生成故事句、阅读覆盖图、结论溯源；标注模型自述
     ▲
事件日志（JSONL）     ← 每一轮的完整请求、响应、工具结果、耗时、token
     ▲
核心 harness         ← agent 循环 + 自研工具、权限闸门、工作区边界
```

举个例子，agent 读取一份 PDF 时，界面默认只显示一句话：

> 读取了 `report.pdf` 第 1–5 页（共 12 页）
> *模型说：想确认第 3 篇的样本量*

第一句由模板从事件生成，是 harness 记录的事实；第二句来自模型自己的说明，以“模型自述”的样式显示。点开后可以看到这一步的原始请求和返回结果。

## 适合谁

**主要用户是非开发者知识工作者**：学生、研究人员、行政与运营人员。他们会把重复的信息整理工作交给 agent，但不知道 harness 是什么，也无法从界面判断 agent 的结论是否可信。

第一版聚焦于用户能看懂结果、能自行核验的任务：

| 场景 | 典型指令 | 解释重点 |
| --- | --- | --- |
| 整理文件夹 | “把下载文件夹按类型和项目归档” | 每一次移动、重命名的意图与确认 |
| 文献汇总 | “从这 12 篇 PDF 里汇总研究方法” | 哪些文件读过、结论来自哪一页 |
| 笔记转待办 | “把这周的会议笔记整理成待办清单” | 每条待办的出处 |

## 快速上手（v0）

需要 [Bun](https://bun.sh) 1.3 或更高版本。

```bash
bun install
```

至少为一家供应商设置 API Key，可以用环境变量，也可以写在项目根目录的 `.env` 文件里（已被 git 忽略）。使用中转站时，再设置对应的地址：

| 供应商 | Key | 地址（可选） |
| --- | --- | --- |
| Anthropic | `ANTHROPIC_API_KEY`（或 `ANTHROPIC_AUTH_TOKEN`） | `ANTHROPIC_BASE_URL` |
| DeepSeek | `DEEPSEEK_API_KEY` | `DEEPSEEK_BASE_URL` |

`.env` 里的值优先于同名的环境变量，所以即使别的工具预先设置了 `ANTHROPIC_BASE_URL` 之类的变量，也不会干扰 Seam。`.env` 里留空的变量会被忽略。

在一个工作区里运行任务，再从日志回放：

```bash
bun src/cli.ts run --provider anthropic --workspace examples/untested-functions "Find all exported functions that have no tests."
bun src/cli.ts replay <sessionId>
```

也可以使用本地 Web 界面：实时显示每一轮，可以在同一个会话里继续追问（重启 Seam 之后也可以），也能逐步回放过去的会话：

```bash
bun run dev
```

打开终端里打印的链接，链接里带有访问令牌，服务只监听 `127.0.0.1`。目前在 Web 界面里，写文件和执行命令一律会被拒绝。

在命令行里，读取和搜索自动放行；写文件和执行命令会在终端里请你确认。每次会话都会记录到 `~/.seam/sessions/<sessionId>.jsonl`（可用 `SEAM_HOME` 修改），包括发给模型的真实 HTTP 请求，鉴权信息已去除。

## 路线图

每一种新的上下文来源，都要在它的解释方式设计好之后才加入。

- [x] **v0 地基**：命令行 agent，4 个工具，完整的事件日志
- [ ] **v1 可解释核心**（目标 2027 年 1 月底）：本地 Web 界面、权限解释、计划审批、任务地图、阅读覆盖图、事实与自述区分、结论溯源
- [ ] **v2 书桌、记忆与 Skills**：可见、可编辑的上下文，项目记忆，中途转向，回退分支，多供应商
- [ ] **v3 外部世界**：浏览器自动化、双视图网页、注入提醒、MCP、反事实回放
- [ ] **v4 不在场**：定时任务与事后回顾

## 不做什么

- 不追求与现有 agent 产品功能全面对齐
- 不做模型内部可解释性（激活、特征、注意力）
- 不把模型的自我陈述当作决策的真实原因来呈现
